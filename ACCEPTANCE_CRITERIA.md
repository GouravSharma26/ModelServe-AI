# Acceptance Criteria and Verification Matrix

## Status vocabulary
- `PLANNED`: not implemented.
- `IN PROGRESS`: partially implemented or not fully verified.
- `DONE`: implementation exists and all listed checks pass with recorded evidence.
- `BLOCKED`: cannot proceed because of a documented dependency or external action.

Never mark `DONE` based on file existence alone.

## Training and model quality
- [ ] Dataset source, version/date, license, target, and schema documented.
- [ ] Input columns and target are validated before training.
- [ ] Train/validation/test separation is explicit.
- [ ] Preprocessing is fit only on training data and included in the saved pipeline.
- [ ] Baseline metric is recorded.
- [ ] Candidate models are evaluated using the same split policy.
- [ ] Metrics include precision, recall, F1, ROC-AUC where valid, PR-AUC where valid, and confusion matrix.
- [ ] Selection rule is documented before final test evaluation.
- [ ] Test set is used for final evaluation, not iterative tuning.
- [ ] Random seeds and package versions are recorded.
- [ ] Artifact manifest contains schema, dataset fingerprint, metrics, version, and checksum.
- [ ] Evaluation output is generated by code and not manually fabricated.

## API
- [x] Valid input produces a valid prediction response. (Verified via test_prediction_success and live HTTP call to /v1/predictions returning label and score.)
- [x] Missing required fields return a stable 4xx response. (Verified via test_prediction_missing_required_field returning HTTP 422 with VALIDATION_ERROR.)
- [x] Wrong data types and invalid categories return stable 4xx responses. (Verified via test_prediction_invalid_category and test_prediction_negative_tenure returning HTTP 422.)
- [x] Unexpected fields are handled according to a documented schema policy. (ConfigDict extra="forbid" enforced; verified via test_prediction_forbidden_extra_field returning HTTP 422.)
- [x] Oversized payloads/batches are limited. (PayloadLimitMiddleware enforces max_payload_bytes; verified via test_prediction_oversized_payload_returns_413.)
- [x] Prediction includes request ID and exact model version. (Response returns request_id and model metadata matching X-Request-ID and active artifact version.)
- [x] Model is loaded once per application lifecycle. (FastAPI lifespan loads model into app.state at startup; verified in test client lifespan and uvicorn startup.)
- [x] Missing/corrupt artifact prevents readiness. (Verified via test_health_ready_unready_returns_503 and test_load_active_model_tampered_artifact_fails_integrity.)
- [x] Client errors do not reveal stack traces or secrets. (Verified via test_safe_500_error_handling; unhandled exceptions return safe INTERNAL_SERVER_ERROR without traceback.)
- [x] OpenAPI contract matches actual responses. (Verified via test_openapi_schema and inspection of /openapi.json.)
- [x] Liveness does not fail solely because PostgreSQL is down. (/health/live returns alive 200 independently of downstream persistence.)
- [x] Readiness reflects whether the service can fulfill its documented contract. (/health/ready returns 200 when active model is verified, 503 when not ready.)

## Persistence
- [ ] Alembic migration can create schema from a clean database.
- [ ] Migration state is versioned and repeatable.
- [ ] Model versions have unique identifiers/constraints.
- [ ] Prediction records include timestamp, model version, outcome, and latency.
- [ ] Raw input payload is not stored by default.
- [ ] Records persist across API and database container restarts.
- [ ] Query errors are handled safely.
- [ ] Database outage behavior matches documented policy.

## Dashboard and monitoring
- [ ] Dashboard connects to actual data.
- [ ] Empty-state behavior is explicit.
- [ ] Model metrics are tied to a specific model version.
- [ ] Prediction distribution reflects persisted prediction events.
- [ ] Request/error/latency figures are computed correctly.
- [ ] No dashboard metric is hardcoded as if it were real.
- [ ] Drift is not described as proof of accuracy decline.
- [ ] Labeled performance is shown only when genuine labels are available.

## Containers and deployment
- [ ] API and dashboard use appropriate separate runtime images.
- [ ] Compose uses a named PostgreSQL volume.
- [ ] Services have health checks where appropriate.
- [ ] Secrets are supplied through environment configuration.
- [ ] `.env` is ignored by Git.
- [ ] Container runs as non-root where feasible.
- [ ] Startup ordering uses health/readiness rather than timing sleeps alone.
- [ ] `docker compose config` succeeds.
- [ ] Images build from a clean checkout.
- [ ] Documented smoke test passes.
- [ ] Public deployment is verified from outside the deployment environment before URL is claimed.

## Engineering quality
- [ ] Unit tests cover schemas, preprocessing, and metrics.
- [ ] API tests cover success and validation failures.
- [ ] Integration tests exercise PostgreSQL.
- [ ] Critical failure paths are tested.
- [ ] CI runs linting and tests.
- [ ] Dependency/security checks are included.
- [ ] Test commands and exact outcomes are recorded.
- [ ] Documentation matches actual commands and endpoints.
- [ ] No secrets or private data appear in repository history or logs.

## Release gate
The Fast Track release is not complete if any critical criterion is unchecked. A known non-critical limitation can remain only if it is documented, the user-facing behavior is safe, and resume claims do not overstate capability.
