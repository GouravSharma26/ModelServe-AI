# Acceptance Criteria and Verification Matrix

## Status vocabulary
- `PLANNED`: not implemented.
- `IN PROGRESS`: partially implemented or not fully verified.
- `DONE`: implementation exists and all listed checks pass with recorded evidence.
- `BLOCKED`: cannot proceed because of a documented dependency or external action.

Never mark `DONE` based on file existence alone.

## Training and model quality
- [x] Dataset source, version/date, license, target, and schema documented. (IBM Telco Customer Churn, Apache-2.0 in TRAINING.md and MODEL_CARD.md.)
- [x] Input columns and target are validated before training. (dataset.py validate_dataset verifies 21 columns and binary Churn target.)
- [x] Train/validation/test separation is explicit. (60/20/20 stratified split in training.py.)
- [x] Preprocessing is fit only on training data and included in the saved pipeline. (ColumnTransformer fitted inside candidate Pipeline.)
- [x] Baseline metric is recorded. (DummyClassifier prior baseline recorded in validation results.)
- [x] Candidate models are evaluated using the same split policy. (LogisticRegression and RandomForest evaluated on identical splits.)
- [x] Metrics include precision, recall, F1, ROC-AUC where valid, PR-AUC where valid, and confusion matrix.
- [x] Selection rule is documented before final test evaluation. (Validation PR-AUC then F1.)
- [x] Test set is used for final evaluation, not iterative tuning. (Evaluated once on selected model.)
- [x] Random seeds and package versions are recorded. (Seed 42 recorded in manifest.json and evaluation.json.)
- [x] Artifact manifest contains schema, dataset fingerprint, metrics, version, and checksum.
- [x] Evaluation output is generated by code and not manually fabricated.

## API
- [x] Valid input produces a valid prediction response. (Verified via test_prediction_success and live HTTP call to /v1/predictions returning label and score.)
- [x] Missing required fields return a stable 4xx response. (Verified via test_prediction_missing_required_field returning HTTP 422 with VALIDATION_ERROR.)
- [x] Wrong data types and invalid categories return stable 4xx responses. (Verified via test_prediction_invalid_category and test_prediction_negative_tenure returning HTTP 422.)
- [x] Unexpected fields are handled according to a documented schema policy. (ConfigDict extra="forbid" enforced; verified via test_prediction_forbidden_extra_field returning HTTP 422.)
- [x] Oversized payloads/batches are limited. (PayloadLimitMiddleware enforces max_payload_bytes on chunked/streamed and Content-Length requests; verified via test_prediction_oversized_payload_returns_413 and test_streamed_oversized_payload_without_content_length_returns_413.)
- [x] Prediction includes request ID and exact model version. (Response returns request_id and model metadata matching X-Request-ID and active artifact version.)
- [x] Model is loaded once per application lifecycle. (FastAPI lifespan loads model into app.state at startup; verified in test client lifespan and uvicorn startup.)
- [x] Missing/corrupt artifact prevents readiness. (Verified via test_health_ready_unready_returns_generic_message and test_load_active_model_tampered_artifact_fails_integrity.)
- [x] Client errors do not reveal stack traces or secrets. (Verified via test_safe_500_error_handling; unhandled exceptions return safe INTERNAL_SERVER_ERROR without traceback.)
- [x] OpenAPI contract matches actual responses. (Verified via test_openapi_schema and inspection of /openapi.json.)
- [x] Liveness does not fail solely because PostgreSQL is down. (/health/live returns alive 200 independently of downstream persistence.)
- [x] Readiness reflects whether the service can fulfill its documented contract. (/health/ready returns 200 when active model is verified, 503 when not ready.)

## Persistence
- [x] Alembic migration can create schema from a clean database. (20261028_0001 initial schema creates model_versions and prediction_records tables.)
- [x] Migration state is versioned and repeatable. (Verified via alembic upgrade head and downgrade base execution.)
- [x] Model versions have unique identifiers/constraints. (model_versions.version has unique index constraint.)
- [x] Prediction records include timestamp, model version, outcome, and latency. (PredictionRecord fields verified via test_record_prediction_persists_telemetry.)
- [x] Raw input payload is not stored by default. (ADR-008 enforced; verified by checking PredictionRecord columns and repository queries.)
- [x] Records persist across API and database container restarts. (PostgreSQL uses named volume postgres_data in docker-compose.yml.)
- [x] Query errors are handled safely. (Monitoring summary handles empty states and database connection dropouts safely.)
- [x] Database outage behavior matches documented policy. (Verified via test_api_prediction_resilience_when_db_down; prediction succeeds even if DB is down.)

## Dashboard and monitoring
- [x] Dashboard connects to actual data. (Streamlit dashboard connects to API and PostgreSQL telemetry.)
- [x] Empty-state behavior is explicit. (Dashboard shows clear informational banner when 0 predictions exist in time window.)
- [x] Model metrics are tied to a specific model version. (Dashboard displays active model version metadata and test split metrics.)
- [x] Prediction distribution reflects persisted prediction events. (Bar chart and breakdown tables reflect live database counts.)
- [x] Request/error/latency figures are computed correctly. (Mean, P50, P90, P95, P99 computed via numpy percentiles.)
- [x] No dashboard metric is hardcoded as if it were real. (All metrics fetched dynamically from API/DB.)
- [x] Drift is not described as proof of accuracy decline. (Documented in dashboard captions and MONITORING_GUIDE.md.)
- [x] Labeled performance is shown only when genuine labels are available. (Labeled test metrics explicitly labeled as offline validation.)

## Containers and deployment
- [x] API and dashboard use appropriate separate runtime images. (Dockerfile.api and Dockerfile.dashboard.)
- [x] Compose uses a named PostgreSQL volume. (Named volume postgres_data.)
- [x] Services have health checks where appropriate. (Postgres pg_isready, API curl /health/live, Dashboard curl /_stcore/health.)
- [x] Secrets are supplied through environment configuration. (.env.example provides placeholders.)
- [x] `.env` is ignored by Git. (Verified in .gitignore.)
- [x] Container runs as non-root where feasible. (USER appuser in Dockerfile.api and Dockerfile.dashboard.)
- [x] Startup ordering uses health/readiness rather than timing sleeps alone. (depends_on service_healthy for api and dashboard.)
- [x] `docker compose config` succeeds. (Validated exit 0.)
- [x] Images build from a clean checkout. (Dockerfile.api and Dockerfile.dashboard built successfully with pinned dependencies and non-root appuser.)
- [x] Documented smoke test passes against live compose containers. (scripts/smoke_test.py verified against running stack.)
- [ ] Public deployment is verified from outside the deployment environment before URL is claimed. (Honest disclosure: local Docker Compose verified; no public cloud deployment claimed.)

## Engineering quality
- [x] Unit tests cover schemas, preprocessing, and metrics.
- [x] API tests cover success and validation failures.
- [x] Integration tests exercise PostgreSQL / persistence.
- [x] Critical failure paths are tested.
- [x] CI runs linting and tests. (.github/workflows/ci.yml runs pip check, compileall, pytest, docker compose config.)
- [x] Dependency/security checks are included.
- [x] Test commands and exact outcomes are recorded.
- [x] Documentation matches actual commands and endpoints.
